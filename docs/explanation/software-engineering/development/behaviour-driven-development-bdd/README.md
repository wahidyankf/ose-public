# Behaviour-Driven Development (BDD)

BDD gives product people, domain experts, and engineers one concrete way to discuss what a change
should do. This guide explains how to apply the
[canonical OSE BDD contract](../../../../../repo-governance/development/behaviour-driven-development.md);
the governance document remains authoritative.

Every testable application, library, and executable tool MUST own canonical Gherkin behaviour,
including technical libraries and pure functions. Unit proof is always required; Integration and
E2E apply only when their real boundaries can express the scenario.

## BDD Framework and Tool Requirements

**REQUIRED BDD Frameworks:**

- **TypeScript (Unit suites)**: `@amiceli/vitest-cucumber` 6.3.0 with Vitest; filesystem,
  database, environment, clock, process, and network dependencies are injected doubles
- **TypeScript (Playwright E2E suites)**: `playwright-bdd` 8.5.1 (step definitions use Playwright
  fixtures; spec files generated by `bddgen` from Gherkin feature files)
- **Other runtimes**: owner-local bindings executed by the project's native test target and
  declared in its README; do not add a parallel standalone Cucumber corpus

**REQUIRED Collaboration Tools:**

- **Example Mapping**: Physical/virtual color-coded cards (blue/yellow/green/red)
- **Three Amigos Sessions**: Weekly scheduled sessions

**PROHIBITED:**

- Standalone Cucumber.js or Jest-Cucumber adapters that bypass the owner-local Nx targets
- Writing step definitions before scenarios
- `@pending`, `@wip`, placeholder steps, or unimplemented active scenarios

## Software Engineering Principles

BDD standards in OSE Platform align with core software engineering principles:

1. **[Documentation First](../../../../../repo-governance/principles/content/documentation-first.md)** - Gherkin scenarios serve as executable specifications written before implementation. Living documentation stays synchronized with code through automated testing.

2. **[Explicit Over Implicit](../../../../../repo-governance/principles/software-engineering/explicit-over-implicit.md)** - Given-When-Then makes preconditions, actions, and outcomes explicit. Ubiquitous language in scenarios eliminates ambiguous requirements.

3. **[Automation Over Manual](../../../../../repo-governance/principles/software-engineering/automation-over-manual.md)** - Scenarios execute automatically in CI/CD. Living documentation updates automatically when behaviour changes.

4. **[Simplicity Over Complexity](../../../../../repo-governance/principles/general/simplicity-over-complexity.md)** - Three Amigos (just 3 roles) prevents bloated meetings. 25-minute Example Mapping time-box prevents over-engineering.

5. **[Reproducibility First](../../../../../repo-governance/principles/software-engineering/reproducibility.md)** - Scenarios in version control ensure reproducible specifications. Deterministic Given steps produce consistent outcomes.

## OSE Platform BDD Examples

### Zakat Calculation Feature

```gherkin
Feature: Zakat Calculation for Gold Wealth

  As a Muslim individual
  I want the system to calculate my Zakat obligation on gold wealth
  So that I can fulfill my Islamic religious duty accurately

  Scenario: Wealth exceeds Nisab threshold
    Given a Muslim individual owns 100 grams of gold
    And the Nisab threshold for gold is 87.48 grams
    And one lunar year (Hawl) has passed since acquisition
    When Zakat calculation is performed
    Then Zakat should be obligatory
    And Zakat amount should be 2.5 grams of gold
```

### Contract Approval Workflow

```gherkin
Feature: Murabaha Contract Approval Workflow

  As a Shariah compliance officer
  I want to review and approve Murabaha financing contracts
  So that all contracts meet Shariah compliance standards

  Scenario: Contract meets all Shariah requirements
    Given a Murabaha contract with 5% profit margin
    And the asset is halal and clearly specified
    And the customer agrees to purchase at disclosed price
    When compliance officer reviews the contract
    Then the contract should be approved
    And the contract status should be "SHARIAH_COMPLIANT"
```

### Campaign Donation Tracking

```gherkin
Feature: Donation Campaign Progress Tracking

  As a campaign organizer
  I want to track donations toward campaign goal
  So that donors can see real-time progress

  Scenario: Donation moves campaign closer to goal
    Given a campaign "Build School" with goal of $50,000
    And the campaign has raised $30,000 so far
    When a donor contributes $5,000
    Then the campaign total should be $35,000
    And the progress percentage should be 70%
    And a "DonationReceived" event should be published
```

## Feature File Organization

**REQUIRED Directory Structure:**

```text
specs/
  apps/organiclever/app-web/behaviours/
    zakat/zakat-calculation.feature
    donation/campaign-management.feature
  libs/web-ui/behaviours/
    button/button.feature
    dialog/dialog.feature
```

**File Naming:**

- Feature files: `[domain-capability].feature` (kebab-case)
- Step definitions: `[feature-name].steps.ts` (TypeScript), `[feature_name]_steps.rs` (Rust)

## Three Amigos Sessions

**REQUIRED Participants:**

- **Business**: Product Owner or Domain Expert (Shariah scholar for Islamic finance)
- **Development**: Lead developer or architect
- **QA**: Test engineer

**REQUIRED Frequency:**

- Weekly sessions for active features
- 45-60 minutes maximum

**REQUIRED Outputs:**

- Feature file with scenarios
- Example mapping cards (blue/yellow/green/red)
- Open questions documented

## Coverage Requirements

**REQUIRED Coverage:**

- Unit proof for every active scenario, with no Unit exemption and a 99% minimum line gate in
  `test:unit`
- Exact static bindings for every applicable layer through `test:coverage:*`, aggregated by
  `test:coverage` and included in `test:quick`
- Happy path scenarios for all user-facing features
- Critical error scenarios (validation failures, permission denied)
- Edge cases identified during Three Amigos sessions
- A passing [Gherkin implementation review](../../../../../repo-governance/workflows/quality/gherkin-implementation-review.md)
  after material changes to features, bindings, exemptions, or coverage machinery

**PROHIBITED:**

- Testing internal implementation details
- Testing framework code
- Multiple scenarios with the same context and observable outcome

## Validation Checklist

Before merging feature files, verify:

- [ ] **Gherkin syntax correct**: Feature, Scenario, Given-When-Then structure
- [ ] **Ubiquitous language used**: Terms match DDD glossary
- [ ] **Scenario independence**: Each scenario runs in any order
- [ ] **Three Amigos approval**: Business, Dev, QA reviewed scenarios
- [ ] **Shariah scholar approval**: Islamic finance features reviewed by scholar
- [ ] **Step definitions implemented**: All Given/When/Then steps have code
- [ ] **Scenarios execute**: All scenarios pass in CI/CD
- [ ] **Living documentation updated**: Docs dashboard reflects latest scenarios

## Principles Implemented

- **[Documentation First](../../../../../repo-governance/principles/content/documentation-first.md)**: By writing Gherkin scenarios before implementation, requirements become executable documentation that drives development and validation.

- **[Explicit Over Implicit](../../../../../repo-governance/principles/software-engineering/explicit-over-implicit.md)**: By using Given-When-Then structure and ubiquitous language, scenarios make preconditions, actions, and outcomes explicit rather than assuming context.

- **[Automation Over Manual](../../../../../repo-governance/principles/software-engineering/automation-over-manual.md)**: By executing scenarios automatically in CI/CD, BDD eliminates manual acceptance testing and ensures living documentation stays current.
