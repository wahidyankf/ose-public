# Business Requirements — Code Harness

## Problem

AyoKoding (`apps/ayokoding-www`) teaches programming through about 180 courses. Most courses show
code in their lessons and keep the same code as files under a `code/` folder. Nothing checks that
code today:

- **Nothing runs it.** Course folders hold 9,470 code files in about 25 languages, plus 901 test-like
  files (counted on 2026-10-09). No Nx target, hook, or workflow compiles or runs any of them. The four
  tutorial quality gates state this outright: "No declared gate compiles or runs tutorial code here,
  so whether an example runs is judgeable."
- **Lessons and files disagree.** A lesson anchors a code block to its file with a bold path line
  such as ``**`learning/code/ex-01-hello-script/example.py`**``. Of the 3,568 anchored blocks,
  1,124 differ from the file they name, and 167 name a file that does not exist. The mismatches are
  spread over 25 courses.
- **Output is unproven.** Lessons print an `**Output**` block under each example. No tool checks
  that the program prints it.
- **Non-deterministic topics are hard to prove.** Distributed systems, concurrency, Raft, actors,
  and CSP examples depend on time, scheduling, and the network, so a naive "run and compare" check
  would be flaky.
- **The tool home is a stray file.** `apps/ayokoding-cli` holds only a `LICENSE`. The earlier Rust
  link checker was retired in commit `d41ea40c4` (PR #226, 2026-08-18), but
  `repo-governance/conventions/structure/command-line-interface/009-tiers-here.md` still lists
  `ayokoding-cli` as a full-bar CLI.

Content plans 06–13 rewrite or audit every course. Without a harness they cannot prove the user's
requirement that "all the code is solid", and plan 14 cannot measure the end state.

## Who This Is For

- **Readers** copy an example, run it, and expect the output the lesson shows.
- **Content authors and content plans 06–13** need a clear contract for where code lives and what
  "done" means for code, plus one command that tells them what is still broken.
- **Plan 14 (`legacy-removal`)** needs a coverage number it can gate on.
- **Maintainers** need the harness to stay cheap: inert for untouched courses, affected-only on pull
  requests, and a full run only monthly or when a toolchain changes.

## User-Stated Requirements (verbatim intent)

- "gw pengen coursenya ini pedagogiknya juga bagus. dan semua kodenya itu solid" — good pedagogy,
  and all the code is solid.
- "kalo butuh tooling deterministic … bisa bikin/ditaroh di apps/ayokoding-cli/ (sekalian bersihin
  aja ini). jadi tetep fokus" — deterministic tooling goes into `apps/ayokoding-cli/`, which is
  cleaned up at the same time, so the work stays focused.
- "bikin pake golang aja di sana. make sure standardnya sama kayak apps yang lainnya" — build it in
  Go, to the same standard as the other apps; "golang + cobra".
- "make sure standard linting dllnya yang ketat ya. coba compare sama hippo" — strict linting and
  the rest; compare it with HIPPO.
- "jangan sampe ada endless loop. harus ada maksimalnya kayak yang lain2nya" — no endless loops;
  every loop has a maximum, as elsewhere.
- Delivery checklists are detailed, split by phase, and end each phase with an explicit completion
  gate.

## Business Goals and Success Measures

| Goal                                 | Measure at merge                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One command proves a course's code   | `ayokoding-cli examples check --course <slug>` exits 0 on the fixture courses and exits 1 with a named finding on each broken fixture                               |
| Lesson code equals runnable code     | The sync check finds every mismatch kind in the fixtures; `examples sync --write` repairs fence bodies from files                                                   |
| No flakiness by construction         | Every run has no network, a fixed environment, and a byte-for-byte second run under different CPU limits                                                            |
| Cheap for untouched content          | With zero `run.yaml` files on `main`, `ayokoding-www:examples:check` runs no container and exits 0 on every PR                                                      |
| Measurable end state                 | `ayokoding-cli examples coverage` reports per-course unit and fence coverage; on `main` at merge it reports 0 covered of 116 applicable courses                     |
| The tool meets the strictness bar    | The parity table shows HIPPO parity or a written reason for every row; `ayokoding-cli:test:quick` is green with 99% coverage on the deterministic core              |
| Content plans have a stable contract | The migration contract and the content skill's new reference module are merged, and the four tutorial gates name the harness as the owner of "does the example run" |

## Business Risks

| Risk                                                        | Mitigation                                                                                                                                                                    |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A full run takes hours on a shared, limited runner pool     | Full runs happen monthly and on catalog changes only, split over 4 shards; pull requests run only affected opted-in courses                                                   |
| Formatters rewrite code files at commit time and break sync | Formatters keep formatting code files; lesson markdown under `content/` stops reformatting fence bodies; `examples sync --write` copies file bytes into fences (decision D21) |
| A toolchain image changes under a tag                       | Every image is pinned by digest; derived images use checksum-pinned downloads                                                                                                 |
| Determinism cannot be fully enforced for wall-clock use     | The harness enforces what it can (network, environment, double run); the remaining rule is judged by the content gates, and the gate text says so                             |
| Static mode becomes an escape hatch                         | `mode: static` accepts only a closed list of reasons, each with a required note; the coverage report lists static units per course                                            |
| `<!-- harness: illustration -->` is overused                | The coverage report counts illustration blocks per course; the content gates judge each one against the written rule                                                          |
| Plans 01–04 edit the same skill or README files             | This plan touches only harness rule text; Phase 7 rebases onto whatever landed first                                                                                          |
