# Business Requirements — ERP Courses

## Problem

AyoKoding (`apps/ayokoding-www`) offers two skills paths for software engineers who build ERP systems:
**Conventional ERP** (27 courses) and **Sharia ERP** (the same 27 plus 3 Islamic-finance courses). Today neither
path can teach anyone, and the way they are wired is held together by a temporary exception:

- **Every course is an empty outline.** Each of the 30 courses has six short pages and 215 to 250 words in
  total (7,043 words over all 30). There are no lessons, no worked examples, no exercises, and no code. A reader
  who follows either path learns nothing past the course titles.
- **The paths have no shape.** Plan 02 turned each ERP path into one flat `all-courses` phase and added a
  `restructurePendingIn` marker that switches off the closure and no-outline-in-core rules, because the courses
  were outlines. Plan 04 added a flat roadmap mode for the same reason. These exist only to wait for this plan.
- **The path pages use internal jargon.** They say "Dangerous 3" and "Dangerous 4" and give no audience
  statement. The reader is never told what they can do after each stage.
- **The courses were planned as "paper" courses.** The 2026-08-16 ERP syllabi chose concept lists with no build
  step. Engineers who build ERP systems need code they can run, change, and reuse: a posting rule, a costing
  method, a reservation under concurrency.
- **The three Sharia ERP courses are risky if done carelessly.** Islamic finance has real differences between
  scholars, schools of law, and national authorities, and its standards change (AAOIFI FAS 39 replaced FAS 9
  from 1 January 2023, and FAS 51 and FAS 52 take effect on 1 January 2027). Content that presents one view as
  the only one, or reads like a ruling, could mislead an institution.

## Who This Is For

- **Readers:** software engineers who build or maintain ERP systems (series decision 16). They can program and
  want to understand the accounting, inventory, production, and control logic that their code implements.
- **Readers in Islamic finance:** engineers building ERP systems for Islamic institutions, who need to know which
  standard applies, where opinions differ, and which questions only their Sharia board can answer.
- **Later plans:** plan 08 (capstones) assumes the finished ERP courses as sources of its projects; plans 11 to
  13 reuse the code conventions shown here.

## Business Risks

| Risk                                                                                                                        | Mitigation                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A course cannot pass a gate within 2 cycles                                                                                 | It is marked `BLOCKED`, restored to its skeleton, recorded, and reported; the batch moves on. The paths are not restructured until the user decides, because one outline would break both paths (decision 6)                                                          |
| A reader treats course text as a Sharia ruling                                                                              | Fixed disclaimer, attributed positions, board-decision callouts, and a content-shape test for the checkable parts                                                                                                                                                     |
| A link sends readers to a harmful page posing as AAOIFI                                                                     | Makers link only pages a person has opened; every AAOIFI URL (including `cis.aaoifi.com`) gets a human tick before the PR is marked ready; the content-shape test fails on any unchecked link                                                                         |
| Standards change while the plan waits in the backlog (FAS 51 and FAS 52 take effect on 1 January 2027)                      | Phase 1 re-verifies every source-register row a course uses; rule SC6 forbids naming a superseded standard except as history                                                                                                                                          |
| Plans 02 to 06 merged with names different from the ones this plan expects                                                  | Phase 0 checks every name on `origin/main` and records the merged names before any change; the merged text wins                                                                                                                                                       |
| The PR is very large (about 8,000 files), and GitHub's "Files changed" view shows only 300 files (1,000 in the new preview) | One commit per wave, checkpoint pushes after waves 3, 6, 9, and 12, per-course gate reports, and a committed execution summary let a reviewer check each course on its own; reviewers and the leak reviews read the commits locally with git, which has no such limit |
| CI cannot run all 30 courses in one job (about 141 minutes sequential)                                                      | Four shards with a 60-minute timeout each; probe P8 measures the real time, and a `[HUMAN]` checkpoint decides on a longer timeout, more shards, or a workflow change if a shard would exceed about 45 minutes                                                        |
| Running many Docker-based examples overloads the machine                                                                    | Every command runs through HIPPO, which admits harness runs one resource budget at a time; at most 3 background agents                                                                                                                                                |
| Deleting the pending mechanism breaks a test or screen that still reads it                                                  | The removal order follows the dependency (readers first, then the module, then the field); a baseline grep in Phase 0 lists every user; the 99% coverage threshold and the end-state grep list prove nothing is left                                                  |
| A PostgreSQL lockfile fails on the CI runner's architecture                                                                 | The first checkpoint push (after wave 3) runs the harness on the CI runner, so a problem surfaces early and is fixed once in the lock text copied to every PostgreSQL course                                                                                          |
| An earlier plan did less than its design says (for example, part of the skills landing work)                                | Phase 0 reads what was merged for each row of the landing split and does only what remains; the expected outcome is "done by plan 06"                                                                                                                                 |
