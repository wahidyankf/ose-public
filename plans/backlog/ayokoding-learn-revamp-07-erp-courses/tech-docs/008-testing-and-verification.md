# 008 — Testing and Verification

What proves the plan works, in the order the delivery uses it: tests for the code that changes, the harness and
the quality gates for the course content, the end-state gate, a manual browser check, and the rollback.
Command names (`UNIT-FE`, `QUICK`, `EX-CHECK`, and the rest) are defined in the Command Reference of
[delivery.md](../delivery.md#command-reference).

## Course Verification

Each course is proven by four things, in this order: the harness pre-check, the mode quality gate, the Content
Quality Gate, and the harness again. [007](./007-execution-batching-and-ledger.md#the-course-loop) defines the
steps. The proof that a course is done is the ledger row plus these commands, run from the execution worktree
root:

| Proof                           | Command                                                                                                                                                                       | Expected                                   |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Code runs, twice, identically   | `EX-CHECK <slug>`                                                                                                                                                             | Exit 0; the summary lists every unit green |
| Lesson fences match files       | `EX-VALIDATE <slug>` and `EX-CHECK <slug>`                                                                                                                                    | No layout or sync finding                  |
| Metadata and word guard         | `CORPUS-GUARD`                                                                                                                                                                | No row names the course                    |
| Content shape (all 30 together) | `UNIT-NODE tests/unit/be-steps/erp-course-completion.steps.ts`, run in Phase 3 once every course is `DONE`; before that the Measure commands give the same numbers per course | Exit 0                                     |
| Indexes are current             | `VALIDATE-INDEXES`                                                                                                                                                            | Exit 0                                     |
| Targets are met                 | The measuring commands in [003](./003-definition-of-done-and-targets.md#measuring)                                                                                            | Every number at or above its target        |

## Rollback

There is no data migration, no environment variable, and no external state. The risk is a bad merge, not bad
data.

| Moment                      | Rollback                                                                                                                                                                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before the PR merges        | Close the PR; the branch is private to the execution worktree. A single course can be restored to its skeleton with the steps in [Blocked Courses](./007-execution-batching-and-ledger.md#blocked-courses).                               |
| After the merge, on `main`  | `rtk git revert -m 1 <merge-commit>` in a new branch and a new PR. This restores the 30 skeletons, the marked manifests, and the mechanism together, because they landed in one PR (D12). `main` is then exactly as it was after plan 06. |
| After production deployment | Production builds from `prod-ayokoding-www`. After the revert merges, run the existing `ayokoding-www-test-local-deploy-prod.yml` workflow to move `main` to that branch, then check the live site (no Vercel MCP is needed)              |

A partial rollback (keep the courses, restore the old path pages) is not supported: the closure rules would fail
for the restored marker-free state. If a path page defect appears after merge, fix it forward with a small PR.
