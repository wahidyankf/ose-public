# 006 — Prerequisites, Metadata, and Closure

Plan 02 revised the `prerequisites` of every course with a written rubric and froze closure rules for the paths.
This plan does not redo that work. It checks, course by course, that the revised list still matches what the
audited lessons teach, changes a list only when the rubric demands it, keeps `estimatedHours` true to the final
text, and keeps every path integrity test green. Three of the 34 courses sit on the AI Engineer path, and one
course, `capstone-solid-core`, has extra obligations because it is a capstone that other courses lean on.

## The Re-Check at the Start of Each Course

CP-1 of every course includes a prerequisite re-check. The maker or fixer reads the course overview's
"Prerequisites" section, the first ten examples, and the capstone brief where one exists, and compares them with the
frontmatter list. The tests are plan 02's rubric, unchanged:

| Test | Meaning here                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------ |
| T1   | The course uses a concept, skill, or artifact that the prerequisite teaches and does not re-teach it                           |
| T2   | The course's own prose does not mark the prerequisite as optional ("helps", "recommended", "companion")                        |
| T3   | Editor edges stay only where the course uses the tool (no course in this plan has one)                                         |
| T4   | Adjacency in an old manifest is never a reason                                                                                 |
| L1   | A language primer is a prerequisite when that language is the course's primary code medium                                     |
| C1   | A capstone requires the courses whose artifacts it integrates, as its overview names them (only `capstone-solid-core` is here) |

An edge is **added** only if T1, L1, or C1 shows a missing one; an edge is **removed** only if it fails T1 or T2
and the prose proves it. Because this plan rewrites prose, the re-check is also the moment an audit could create a
new dependency by accident (a rewritten lesson that now uses Python, or a networking course whose loopback units
now need a language it did not list). The re-check runs again at the end of CP-4, after the last text change, and
the ledger records "unchanged" or the edit.

Three groups of courses deserve a named look, because their medium or their toolchain moves during the audit:

- `advanced-networking` and `networking-essentials`: the units become Python loopback and model units. Plan 02
  already added `just-enough-python`; the re-check confirms the language is the primary medium after the rewrite
  (L1) and that no unit needs a second language.
- `distributed-systems` and `build-your-own-raft`: the first is Python models; the second is Go. The lists
  (`networking-essentials` and `concurrency-and-parallelism` for the first; `just-enough-go` and
  `distributed-systems` for the second) stay unless the rewritten units use something else.
- `graph-databases`: plan 02 removed `nosql-databases`. The re-check confirms that the five relational-contrast
  units use `sql-essentials` (SQLite) and nothing from the NoSQL course.

**Who edits.** Makers and fixers never edit any `_index.md` frontmatter. The coordinator edits a course's
`prerequisites` and `estimatedHours` in the CP-6 commit, with the integrity tests below run first. If the re-check
changes a list, the course brief in the corpus is edited in the same commit, because this plan is the custodian of
the briefs while it runs.

## `estimatedHours`

Plan 03 derives `estimatedHours` from the course's size, with the formula
`max(1, round((proseWords / 200 + max(inlineCodeLines, codeFileLines) / 10) / 60))`, and a drift test that prints
"Expected estimatedHours for every non-outline course". This plan changes the words and the code lines of all 34
courses, so nearly every value changes, and for the 14 authoring courses it changes a lot. The coordinator
recomputes it after the **last** edit of each course (CP-6), reading the expected value from the drift test, never
by hand, and never before CP-4 ends. A course whose value changes is not a reason to touch a manifest: the catalog
and the path pages read the frontmatter value.

A large jump is a signal, not an error. If the printed value is more than double the snapshot for a course that
was not rewritten, or lower than the snapshot for one that grew, the coordinator looks for a missing section or a
bloated one, records the cause in the ledger, and keeps the printed value.

its core is exactly the goal plus its transitive prerequisites, stopping at the courses the path assumes (series
decisions 7 and 9). Plan 11 read the core as 12 courses with four assumed (`api-design`, `backend-essentials`,
`just-enough-bash`, `sql-essentials`) and a set of extension courses. Three courses of this plan are on that path at baseline,
a fourth (`sql-essentials`) is assumed by it after plan 08, and none is in the core:

| Course                                                                                                          | Position on the path at baseline (2026-10-09, 26 courses) | Role after plan 08 (Phase 0 reads the merged manifest) | Prerequisites after plan 02                                                  |
| --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| [`sql-essentials`](../syllabus/courses/sql-essentials.md)                                                       | not listed (assumed by the path after plan 08)            | assumed                                                | `just-enough-python`                                                         |
| [`data-structures-and-algorithms-essentials`](../syllabus/courses/data-structures-and-algorithms-essentials.md) | 2                                                         | extension (expected)                                   | `just-enough-python`                                                         |
| [`computer-architecture`](../syllabus/courses/computer-architecture.md)                                         | 3                                                         | extension (expected)                                   | `computer-science-foundations`, `just-enough-python`                         |
| [`data-engineering`](../syllabus/courses/data-engineering.md)                                                   | 7                                                         | extension (expected)                                   | `sql-essentials`, `advanced-sql-and-query-performance`, `just-enough-python` |

Because the closure stops at an assumed course, a change to `sql-essentials`'s own prerequisites cannot change the
core, and the extension courses are not in the closure at all. The expected result of CP-1 and CP-6 for these four
is therefore **no effect on the AI core**, and the generic tests above are enough. The expectation is checked, not
trusted: Phase 0 computes the closure from the merged manifest (the same computation as rule R6) and records which
of the 34 courses it contains. The expected intersection is empty.

**Rule AI-1 (plan 11's rule, applied here unchanged).** A prerequisite change on any of the 34 courses that is in
the AI core closure, or that would add a course to it, is made only if both hold:

1. The rubric requires it (T1, L1, or C1 with prose evidence).
2. After the edit, `path-model-integrity.unit.test.ts` (R4, R6, R7, R10) and `careers-ai-manifest.unit.test.ts`
   still pass with the current AI manifest.

If condition 2 fails, the closure would change, which changes the product (the core's size and the path's phases).
The coordinator does not make the edit and does not decide: it records a `needs-decision` row in the ledger with the
evidence, continues with the course on its present list, and raises the row at the next checkpoint push. The user
may then choose to update the AI manifest in the same PR (the manifest's phases and `assumes`,
`careers-ai-manifest.unit.test.ts`, and the path page copy, following plan 08's recomputation: RED on R6 printing
the expected core, reconcile, GREEN) or to keep the edge.

**Why not change the AI manifest eagerly.** Plan 08 shrank the core on purpose and flagged it to the user. A second,
silent change to the core in an audit PR would be the wrong place for it.

## `capstone-solid-core`

`capstone-solid-core` is the only capstone in this plan. Plan 08 rewrites eight skeleton capstones; this one is
filled but has a different layout (one 15,009-word page and 35 files in a root `code/` folder), and plan 08 left it
to the audit plans. This plan brings it to plan 08's capstone contract and to the definition of done
([002](./002-definition-of-done-and-audit-method.md)). The mode is Annotated Concept in its standard mode, 45
worked examples in five themes, as decision D9 records in [008](./008-decision-records.md). Its slug, title, and place
in every path stay.

Plan 08's capstone content-shape test is bound to the capstone courses. Phase 0 checks whether it enumerates the
eight capstones by name, by glob, or by `format: capstone`. If by glob or by format, `capstone-solid-core` is covered with no edit; if by name, this plan

**The shared-copy row (CC6).** If SP13 shows that the git demo and the app need a file in both toolchains, the
coordinator adds a row naming the two paths to the CC6 pairs table in plan 08's step file, writing the failing
byte comparison first (RED), then copying (GREEN). If every unit holds one toolchain and shares nothing, no row is
added. The step file's merged name is read in Phase 0.

### Who leans on it

`capstone-real-world-delivery` (plan 08) lists `capstone-solid-core` in its `prerequisites` under rule C1: the
service shape comes from it, and that capstone ships its own copy of the shape (CL3). Plan 08's handoff table gives
plans 10 to 13 a duty: before a course is rewritten, search `capstone-*/learning/overview.md` for its slug, read the
`relies-on` row, and confirm the new text still teaches the named concepts. This plan owes that duty, in two places:

1. CP-1 of `capstone-solid-core` searches for the slug and records the rows found (expected: one, in
   `capstone-real-world-delivery`).
2. CP-6 confirms, against the restructured text, that every concept named in those rows is still taught, and edits the
   row and the restating paragraph in the same commit if one is not. A concept that moved to another page is still
   present; a concept that disappeared is a finding, and the course is not DONE until the row and the text agree.

`capstone-first-working-software` is the opposite direction: it is plan 13's course, audited after this plan, and
it is the starting app of `capstone-solid-core`. The relies-on row is written from the course's present overview. This
plan cannot edit plan 13, so the assumption is recorded in [README](./README.md#cross-plan-assumptions): plan 13 keeps the
app shape the row names, or updates the row in the same commit as its change.

further edit.
