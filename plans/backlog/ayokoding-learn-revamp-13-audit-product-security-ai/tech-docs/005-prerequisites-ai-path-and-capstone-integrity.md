# 005 — Prerequisites, the AI Engineer Path, and Capstone Integrity

Plan 02 revised the `prerequisites` of every course with a written rubric and froze closure rules for the paths. This
plan does not redo that work. It checks, course by course, that the revised list still matches what the audited lessons
teach, makes a change only when the rubric demands it, and keeps every path integrity test green. Three things need
extra care here: the AI Engineer path's core is a computed closure and eight of the 45 courses sit in it; five of plan
08's capstones restate this plan's courses in `## What this course relies on` tables; and two existing capstones of
this plan gain a `learning/` folder, which changes one of plan 03's Start-button cases.

## The Re-Check at the Start of Each Course

CP-1 of every course includes a prerequisite re-check. The maker or fixer reads the course overview's "Prerequisites"
section, the first ten examples, and the capstone brief, and compares them with the frontmatter list. The tests are
plan 02's rubric, unchanged:

| Test | Meaning here                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------- |
| T1   | The course uses a concept, skill, or artifact that the prerequisite teaches and does not re-teach it    |
| T2   | The course's own prose does not mark the prerequisite as optional ("helps", "recommended", "companion") |
| T3   | Editor edges (Neovim) stay only where the course uses the tool; none of the 45 courses uses one         |
| T4   | Adjacency in an old manifest is never a reason                                                          |
| L1   | A language primer is a prerequisite when that language is the course's primary code medium              |
| C1   | A capstone requires the courses whose artifacts it integrates, as its overview names them               |

An edge is **added** only if T1 or L1 or C1 shows a missing one; an edge is **removed** only if it fails T1 or T2 and
the prose proves it. Because this plan rewrites prose (and writes 487,871 words of it), the re-check is also the moment
the audit could create a new dependency by accident: a rewritten lesson that now uses Python, SQL, or the
Model Context Protocol. The re-check runs again at CP-4's end, after the last text change, and the ledger records
"unchanged" or the edit.

**Who edits.** Makers and fixers never edit any `_index.md` frontmatter. The coordinator edits a course's
`prerequisites`, `estimatedHours`, and (for two courses) `format` in the CP-6 commit, with the integrity tests below run
first.

## `estimatedHours`

Plan 03 derives `estimatedHours` from the course's size, with the formula
`max(1, round((proseWords / 200 + max(inlineCodeLines, codeFileLines) / 10) / 60))`, and a drift test that prints
"Expected estimatedHours for every non-outline course". This plan changes words and code lines in every one of the 45
courses, so most values change. The coordinator recomputes it after the **last** edit of each course (CP-6), reading
the expected value from the drift test, never by hand. A course whose value changes is not a reason to touch a manifest:
the catalog and the path pages read the frontmatter value.

**Rule AI-1 (decision D14).** A prerequisite change on any of the eight core courses, or on a course that one of them
requires inside the closure, is made only if both hold:

1. The rubric requires it (T1, L1, or C1 with prose evidence).
2. After the edit, `path-model-integrity.unit.test.ts` (R4, R6, R7, R10) and `careers-ai-manifest.unit.test.ts` still
   pass with the current AI manifest.

If condition 2 fails, the closure would change, which changes the product (the core's size and the path's phases). The
coordinator does not make the edit and does not decide; it records a `needs-decision` row in the ledger with the
evidence, continues with the course on its present list, and raises the row at the next checkpoint push. The user may
then choose to update the AI manifest in the same PR (the manifest's phases and `assumes`,
`careers-ai-manifest.unit.test.ts`, and the path page copy, following plan 08's recomputation: RED on R6 printing the
expected core, reconcile, GREEN) or to keep the edge. Extension and assumed courses need only the generic tests above;
for an assumed course, the check also confirms the `assumes` list is still exact.

**Why not change the AI manifest eagerly.** Plan 08 shrank the core from 25 to 12 courses on purpose and flagged it to
the user. A second, silent change to the core in an audit PR would be the wrong place for it.

**Order inside the path.** The AI courses of this plan fall in waves 3 to 15, and the core courses in waves 3 to 9, so
each core course is audited after the core courses it requires (`creating-ai-powered-apps` in wave 3, `agentic-ai` in
wave 4, `the-agent-loop` in wave 5, `agent-tools-and-mcp` in wave 6, `agent-context-and-memory` in wave 8,
`agent-permissions-and-sandboxing` and `agent-orchestration-subagents-and-observability` in wave 9, and
`async-python-and-fastapi-services` last, in wave 15, because `backend-essentials` and `api-design` come first).

## Capstones That Gain a Learning Folder

Plan 03's feature `course-landing-header.feature` has three Start-button cases: Start opens the learning overview;
Start falls back to the first learning page (a `learning/` folder without an overview); and Start falls back to the
course overview (a course with no `learning/` folder, "shape 3"). Plan 08 gave every skeleton capstone a
`learning/overview.md`, which removed the real-content E2E binding of the second case, and it left the third case
bound to `capstone-first-working-software`, with a duty: whoever gives that course a `learning/` folder rebinds the
step.

This plan gives both `capstone-first-working-software` and `capstone-full-stack-app` a `learning/` folder (class X12:
neither has one today). The duty falls here:

1. **Phase 0** lists the courses with no `learning/` folder (`rtk git ls-tree` over the course folders) and records the
   set. If a course other than these two remains, the E2E step of "Start falls back to the course overview" is
   rebound to that course in the commit of `capstone-first-working-software`.
2. **If none remains**, the commit of the last of the two capstones (wave 11, `capstone-first-working-software`)
   records an exemption for the E2E binding, as plan 08 did for the second case: the scenario text and its Unit
   binding (fixture trees for all three shapes) do not change, the integration exemption's alternative proof moves to
   `ayokoding-www:test:unit`, an `@e2e-exempt` tag with the reason "no course lacks a learning folder once every
   capstone has one, and the browser-test server substitutes manifests only, so the shape cannot be supplied at that
   boundary" is added, and the step bound to `capstone-first-working-software` is removed from
   `apps/ayokoding-www-fe-e2e/tests/e2e/steps/course-landing-header.steps.ts`.
3. Before the edit, Phase 0 confirms the merged Unit binding is fixture-based; if it is not, a fixture-based proof is
   added first (RED, GREEN).
4. The manual check in Phase 10 opens Start on both capstones and confirms it lands on `learning/overview`.

The exemption is flagged to the user in the README because it removes one end-to-end binding; the rule it protects stays
proved by Unit.
