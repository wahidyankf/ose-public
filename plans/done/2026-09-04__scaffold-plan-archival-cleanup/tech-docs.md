# Technical Documentation — Scaffold Plan-Archival Cleanup Steps

## Who This Is For

You are executing this plan with no prior context. Read this before opening `delivery.md`.

## Concepts You Need First

**Skill reference module.** A Skill is `.claude/skills/<name>/SKILL.md` plus `reference/*.md`
modules it links. `plan-maker` reads `plan-creating-project-plans`; `plan-checker` reads
`plan-validating-quality`; `plan-fixer` reads `plan-applying-fixes`. Editing what an agent does
usually means editing a reference module, not the agent file.

**Skill mirrors.** Skills authored under `.claude/skills/` have non-vendored mirrors under
`.agents/skills/`, generated by `npm run generate:bindings` and verified by `npm run validate:sync`.
OpenCode reads `.claude/skills/` natively and needs no mirror. Never hand-edit a mirror.

**Rules surface.** A Skill reference module that states an authoring or validation obligation is a
rules surface. Changing one runs through
[rules-propagation](../../../repo-governance/workflows/rules/rules-propagation.md), not an ad-hoc
edit.

## Design Decisions

### D-1: Extend the existing worktree rule, do not mint Rule 22

`plan-validating-quality` numbers its rules to 21. The obvious move is
`rule22-archival-cleanup-completeness.md`.

**Chosen instead: extend
`.claude/skills/plan-validating-quality/reference/rule10-worktree-specification-validation.md`.**
Rule 10 already owns worktree declaration and the branch inventory. Cleanup is that subject's
terminal state, not a new subject, and the propagation workflow routes a statement to the narrowest
surface that already binds it.

A new numbered rule would also cost more than a checkbox: a new shard needs a link in its folder
`README.md` **and** in the parent index, or the readme-completeness gate fails the push as an
orphan — and the same in the sibling repository, whose shard filenames differ.

**This decision is confirmed, not assumed, at the propagation run's Step 4.** If Rule 10's shard is
at its word-budget ceiling, Step 5's eviction protocol applies — and a threshold is never raised to
make room. Only if eviction is genuinely impossible does a new shard become correct.

### D-2: The template links out, it does not restate the procedure

`branch-cleanup.md` carries the proof gates, the squash-merge caveat, the `-D` authorization, and
the never-delete list. Copying any of that into the template creates a second copy that drifts.

The template states only what is plan-specific and links out for the rest:

1. Classify every `Delivery Branch Inventory` entry as delivered, unused, or retained/escalated.
2. Remove each worktree the plan provisioned, non-force, from the repository root.
3. Complete the canonical branch cleanup for every plan-created branch, then `git worktree prune`.

Step 1 is the one with no other home: the inventory is a plans-convention artifact, and this is
where it is finally consumed.

### D-3: Verify the check in both directions before landing

A presence check is trivial to write so that it never fires. AC-2 is a Scenario Outline with a
firing row and a non-firing row for exactly this reason: a check verified in one direction is half a
check, and the half usually missing is the one that matters.

The main-mode row is not decoration. A `main-to-pr` or `main-to-origin-main` plan provisions no
worktree and declares `Worktree: not applicable`. A naive check would flag every one of them.

### D-4: Enumerate live plans before landing, not after

The check runs against plans that already exist. At authoring time `plans/in-progress/` and
`plans/backlog/` hold a small number of plans, but that number is discovered at execution, not
assumed here. Every finding it produces is fixed in this delivery or recorded with its reason —
landing a check that immediately reddens unrelated work is not shipping.


The same tree applies to the private sibling, against its own shard filenames. Nothing is copied between
repositories; the semantic delta is restated in each.

### More Detail

`plan-applying-fixes`'s exact recipe module is discovered with
`rtk grep -rln "rule10\|worktree" .claude/skills/plan-applying-fixes/reference/` rather than named
here, because the recipe catalog is organized by finding type and the mapping is not stable enough
to hardcode at authoring time.

The `plans/in-progress/*/delivery.md` line is bounded by AC-4: its members are exactly the plans the
new check flags, enumerated before the check lands.

## Dependencies

- No new package, tool, or runtime dependency.
- Existing commands only: `npm run generate:bindings`, `npm run validate:sync`,
  `apps/rhino-cli/scripts/rhino-bin.sh md links validate`, and the `rules-quality-gate`.
- No dependency on `update-tmp-folders`. The two plans touch disjoint files and may land in either
  order.

## Rollback

`git revert` the delivery commit, then re-run `npm run generate:bindings` to confirm the mirror tree
is clean. Docs-only in both repositories; no runtime state, no code, nothing to migrate.
