5. STRUCTURAL DEVIATION FROM THE CHECKBOX WORDING (deliberate, flagged)
================================================================================

The checkbox and tech-docs/004's file-impact tree both name
`specs/apps/ose/id-be/architecture/*.md` and `specs/apps/ose/id-web/architecture/*.md`.
The enforced repository convention places the canonical document at the owner root as
`<owner>/architecture.md`, not in an `architecture/` directory:

  - repo-governance/conventions/structure/specs-directory-structure/logical-owner-corpus.md
    requires exactly three owner entries: README.md, architecture.md, behaviours/.
  - canonical-app-spec-tree.md states the C4 zoom levels are sections of one document
    rather than folders.
  - apps/rhino-cli/src/RhinoCli.Application/src/Specs.fs literally tests
    `treeHasFile tree (ownerRel + "/architecture.md")` to detect a corpus, and
    `specs/apps/ose/be`, `lms-be`, and `app-web` all follow that shape.

Both were satisfied rather than one being chosen: the canonical `architecture.md` sits at
each owner root, and the detail views live in the `architecture/` companion directory the
checkbox names, indexed from the parent. This mirrors the repository's existing
progressive-disclosure pattern (`X.md` beside an `X/` companion directory, as used
throughout repo-governance). `specs structure validate --app ose` returns 0 findings,
which it would not if the canonical file were missing.

Recommended plan amendment: tech-docs/004's file-impact rows for both owners should read
`architecture.md [N]` plus `architecture/*.md [N]` rather than `architecture/*.md` alone.

6. CORRECTION TO A STATED PREMISE ABOUT THE WEB SHELL
================================================================================

The task framing asserted that ose-id-web "independently reports its own health/availability
state (it does NOT proxy the backend's health)". Verified against tech-docs/001 and
tech-docs/006, the accurate statement is narrower:

  - tech-docs/001 line 55: ose-id-web "Owns a Next.js shell, OSE design tokens/components,
    a SERVER-SIDE BACKEND-HEALTH ADAPTER, accessible status presentation, configuration
    validation, and non-local startup guard."
  - tech-docs/002 requires the public backend URL http://127.0.0.1:8501 in web configuration.
  - tech-docs/006 web status packet: backend-status unavailability returns a sanitized 503
    status page; prd.md renders Backend / PostgreSQL / Schema rows.

So the shell DOES read the backend's readiness, on its own server side. What it does not do
is proxy: it exposes no health route of its own, forwards no backend response body, mirrors
no backend status code onto an API surface, and never reveals the backend origin to the
browser. Its own availability (that the page answered at all) stays distinguishable from the
backend rows it renders. The web architecture documents state exactly that, and do not claim
the shell is health-independent.
