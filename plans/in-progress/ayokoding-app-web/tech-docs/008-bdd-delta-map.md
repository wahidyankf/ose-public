# BDD Delta Map

This companion maps every acceptance criterion added on 2026-11-28 to the durable feature file and the
exact scenario title that carries it, and states which layer proves it. The full Gherkin for HTTP
operations is in [004](./004-api-contract-delta.md); the PRD holds the representative journeys. The
canonical text lands in `specs/apps/ayokoding/web/behaviours/` in the unit named in the last column.
Titles below are the durable titles: they contain no plan slug, phase, acceptance-criterion id, or parenthetical annotation.

Layer vocabulary: **Unit** is a godog scenario over in-memory doubles in `apps/ayokoding-web/tests/bdd`;
**Integration** is a godog scenario over `httptest` and the real filesystem in
`apps/ayokoding-web/tests/bdd-integration`; **E2E** is a Playwright scenario in the home named. No scenario below is exempt at any layer its row names; the redirect export has no scenario, because its Unit drift test and the recorded inline command prove it (see the redirect drift paragraph in [006](./006-parity-program-design.md)). The two startup-refusal scenarios are bound at E2E through the
process boundary: the built binary is started with the bad input and must exit non-zero with its message.

Pre-amendment 004 packet scenarios that this map does not list are design illustrations. Unit tests and
the manual HTTP recipes in `delivery.md` prove their behaviour, and they are not durable corpus titles.

## New and changed scenarios

Action `add` creates the scenario, `edit` changes an existing one, and the feature path is relative to `specs/apps/ayokoding/web/behaviours/`. Tags in the Tags column are the new ones only. Selection is by file, not by tag. The be home binds the nine HTTP-only feature files listed in the "HTTP-only feature files" section below, and its Playwright configs select data mode only: the real-corpus config runs them with `not @fixture`, and the fixture config with `@fixture and not @fixture-unavailable`. From `P5-Cache` a third config, unavailable-catalog, runs the `@fixture-unavailable` scenarios; until then the be home has two configs and no `@fixture-unavailable` scenario. The fe home binds every other feature file under `behaviours/`. Each `@fixture` scenario is listed with its reason in `evidence/P3-E2E/fixture-scenarios.md`, and each `@fixture-unavailable` scenario is added to that file by `P5-Cache`.

the new product, so no scenario of that kind enters the corpus. The harness
report and the exceptions file in `evidence/P6-Harness/` are the proof. When the harness finds an
observable design contract worth keeping (a breakpoint at which the sidebar collapses, a token that
drives focus rings), the unit that fixes it adds it to `shell/bilingual-shell.feature` as an ordinary
scenario with full bindings. AC-21 to AC-23 are repository-structure outcomes proved by inspection and
by the suites running; they are not product behaviours.

## HTTP-only feature files

The be home binds exactly these nine feature files, listed relative to `behaviours/`. No file mixes the two homes:

- `content/content-tree-routes.feature` (new)
- `content/content-rendering-http.feature` (moved scenarios, below)
- `navigation/url-compatibility.feature` (new)
- `navigation/routes-and-navigation-http.feature` (moved scenarios, below)
- `navigation/entry-pages-http.feature` (new: the browse page and the tools index)
- `search/search-http.feature` (one moved scenario and one new scenario)
- `discovery/discovery-documents.feature` (wholly HTTP; its scenarios stay in place)
- `discovery/http-caching.feature` (new)
- `local-development/local-development-http.feature` (one moved scenario and two new scenarios)

`ayokoding-web-fe-e2e` binds every other feature file under `behaviours/`, including the browser files that
keep their remaining scenarios: `content/content-rendering.feature`, `navigation/routes-and-navigation.feature`,
`navigation/entry-pages.feature` (the locale landing page), `search/search.feature`, and
`local-development/local-development.feature` (which keeps the two startup-refusal scenarios).

The unit that creates a file adds those lines. The `(@fixture)` notes are tag annotations for this table, not part of the titles.

## Fixture-mode `no-store` proof

The catalog-failure scenario, "A catalog failure response is not stored", is bound at E2E only by the be home's
unavailable-catalog config, which `P5-Cache` creates with this scenario as its first. Its Unit proof of the `Cache-Control: no-store` header is the Go unit test
`apps/ayokoding-web/internal/web/cache_test.go`, created by `P5-Cache`, which asserts that every response the
unavailable-catalog double produces carries that header. The Unit godog scenario of the same title in
`apps/ayokoding-web/tests/bdd` binds the Gherkin; the Go test is the proof of the header. The search-fragment and
missing-page examples of "Responses that must not be stored say so" run in the be home's real-corpus config.
