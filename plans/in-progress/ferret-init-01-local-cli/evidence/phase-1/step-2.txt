## Classification (four facts per obligation)

Audience rows follow Step 2's table. "Governance layer" = read when the contributor reaches the activity, so the activity
itself leads them to the rule at no instruction-surface cost. Vendor neutrality: a rule is vendor-specific only when it cannot be
stated without naming a harness, vendor tool, or vendor path. Naming a language toolchain (uv, pytest, Ruff) is not vendor-specific
in this sense: the existing development-layer docs already name Vitest, Playwright, Reqnroll, Godog, Coverlet, and JaCoCo.

| ID    | Subject (narrowest noun)                                         | Audience and consequence                                                   | Neutrality                                 | Layer                          |
| ----- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------ |
| PYR-1 | a Python CLI owner project's mandatory Nx targets                | reached when scaffolding/reviewing project.json: governance layer          | neutral                                    | development (how to develop)   |
| PYR-2 | a dedicated Python CLI E2E project's mandatory Nx targets        | same activity: governance layer                                            | neutral                                    | development                    |
| PYR-3 | static pytest-bdd binding recognition                            | reached when writing bindings/adding an adapter: governance layer; also a machine check | neutral                       | development + application (validator) |
| PYR-4 | owner `test:unit` line-coverage threshold shape                  | reached when authoring `test:unit`: governance layer; also a machine check | neutral                                    | development + application      |
| PYR-5 | project tags for a Python project                                | reached when tagging a project: governance layer; vocabulary is a declaration | neutral                                 | development                    |
| PYR-6 | FERRET lifecycle capture registrations (wrapper/plugin)          | harness maintainers, when they touch a binding: one agent skill + catalog  | **vendor-specific** (names three harnesses) | skill surface + binding-examples catalog (`docs/reference/platform-bindings.md`) |
| PYR-7 | the generated route for the canonical harness-compatibility skill | a machine only: declaration + validator; prose only as pointer             | vendor-specific (names the Claude profile route) | skill surface + binding-examples catalog |

Placement is therefore a consequence of these facts, not a parallel judgement (Step 4 spends them):
- Instruction-surface candidacy: none. No obligation changes behaviour before a file is opened; each is reached through its
  activity. AGENTS.md (715 words, fail threshold 750) and CLAUDE.md are not touched; the vendor-neutral canonical file is the only
  instruction file that could have been a candidate and no shim is a candidate for a neutral rule.
- Fallback layers recorded for Step 4: PYR-1/2 -> development/infra/nx-targets; PYR-3/4 -> development/infra/nx-targets (behaviour
  coverage) plus the static validator; PYR-5 -> development/infra/nx-targets tag convention; the setup workflow that ships Python
  (`repo-governance/workflows/infra/development-environment-setup`) is a discoverability surface whose current sentence
  "This repository ships no Python application or library" becomes false when this delivery lands; PYR-6/7 -> the
