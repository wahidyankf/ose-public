== DEVIATIONS AND FOLLOW-UPS ==

1. The checklist's stated command `npm exec redocly -- lint ...` is real and correct: the
   `redocly` binary resolves to @redocly/cli 2.22.1 from the root package.json. No correction
   was needed (unlike the earlier `specs validate` routing correction in specs.txt).
2. Layout: the four sibling contracts (ose/be, ose/lms-be, roots/be, organiclever/be) split
   openapi.yaml into paths/ and schemas/ files and register an Nx project (project.json,
   .spectral.yaml, generated/ bundle). This contract is a single self-contained document with
   internal $ref reuse because tech-docs/004's file-impact ledger admits exactly
   `contracts/openapi.yaml [N]`; a project.json would register a new Nx project that no phase
   has authorized yet. Follow-up for the implementation phase that creates `ose-id-be`: add
   `specs/apps/ose/id-be/contracts/project.json` (+ `.spectral.yaml`) so this contract is linted
   by a cached Nx target and feeds codegen, and amend the file ledger for those paths.
3. `specs/apps/ose/id-be/contracts/README.md` is not named in the file ledger either, but the
   specs directory-structure convention requires a README index in every spec directory, so it
   is mandatory scaffolding for the admitted `contracts/` path.
4. No OpenAPI operation was added for a wrong-method request against a disabled path. tech-docs/006
   states those fall through to the framework's ordinary 404 without a capability code and records
   RETAIN as none, and prd.md AC-FND-06's table has no wrong-method row. Declaring one would have
   created an operation that neither source authorizes. The rule is documented in prose inside
   `info.description` and the Disabled Capabilities tag description instead.
5. `specs/apps/ose/id-web/behaviours/foundation/README.md` needed a one-line scenario-count update
   (1 -> 3) because `specs counts validate` reads it; no other part of a prior lane's file was
   touched.
