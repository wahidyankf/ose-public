# Multi-Harness Binding Convention

- [Multi-Harness Binding: Principles and Purpose](./principles-and-purpose.md) — The core principles this binding model implements, and the three failure modes (instruction duplication, silent shadowing, unbounded proliferation) it prevents. Read this first to understand why the repository needs a governed multi-harness binding model rather than ad-hoc per-tool files.
- [Multi-Harness Binding: Scope](./scope.md) — The exact list of what the multi-harness binding convention governs and what it explicitly does not — instruction content, catalog entries, and the compatibility-audit workflow. Read this to check whether a specific binding question (for example, AGENTS.md content itself, or the compatibility-audit workflow) is covered by this convention or by a sibling document.
- [Multi-Harness Binding: Canonical Surface, Binding Tiers, and No-Shadowing (Rules 1-3)](./rules-1-to-3.md) — Rules 1 through 3 — AGENTS.md as the single instruction source, the Tier-1/Tier-2 binding model, and the hard no-shadowing rule for higher-precedence harness files. Read this when deciding whether a harness needs a committed binding file, or when auditing whether a harness-specific file improperly shadows AGENTS.md.
- [Multi-Harness Binding: Mechanical Generation and the Parity Guard (Rules 4-5)](./rules-4-to-5.md) — Rules 4 and 5 — every required binding file must be generated by CLI tooling from AGENTS.md, and the deterministic `harness-adapters` gate that enforces byte-equality plus catalog completeness. Read this when adding or changing a generated binding file, or when investigating a `harness-adapters` gate failure.
- [Multi-Harness Binding: npm Script Naming and Catalog Requirement (Rules 6-7)](./rules-6-to-7.md) — Rules 6 and 7 — the harness-neutral generate:/validate: npm script naming constraints, and the requirement that every committed binding directory have a catalog entry. Read this when naming a new npm script that produces or validates binding artifacts, or when adding a new binding directory and its catalog row.
- [Total Ownership of Binding Files (Rule 8)](./ownership-classes.md) — The three ownership classes every tracked binding file must carry — generated, vendored, or source — with no fourth class and no unclassified residue. Read this when adding a file to a binding directory, when deciding whether a third-party payload belongs in the repository, or when `harness adapters validate` names a file you did not expect.
- [Cross-Harness Config Parity (Rule 10)](./config-parity.md) — Editing one harness's hand-authored config obliges the equivalent change in every other supported harness's config, or a recorded reason why it is absent. Use when changing any hand-authored harness configuration file, or when recording why a setting exists for one harness and not another.
- [Divergence Triage and Reviewed Promotion (Rule 9)](./divergence-triage.md) — Rule 9 — generation stays one-way by default, divergence is detected by content and never by timestamp, and promoting a mirror edit back into canonical source is a human-reviewed patch rather than an automatic write. Read this when a hand edit made inside a generated mirror needs keeping, or when `harness adapters validate` fails and you are deciding which side to change.
- [Multi-Harness Binding: Examples](./examples.md) — Worked PASS and FAIL examples of the binding rules — Tier-1 with no committed file, Tier-2 generated pointers, thin pointers, and the failure modes each rule prevents. Read this when you need a concrete pattern to check a specific binding decision against, or when explaining why a proposed binding file was rejected.
- [Platform Binding Examples](./platform-binding-examples.md) — The concrete, per-harness file names and binding-tier assignments that instantiate the Multi-Harness Binding Convention's rules — vendor-specific content, exempt from the vendor-audit scanner under this heading. Read this when you need the actual file names that shadow AGENTS.md, or the current per-harness Tier-1/Tier-2 assignment for a specific coding-agent harness.
- [Multi-Harness Binding: Tools and Automation](./tools-and-automation.md) — The Rhino subcommands and npm scripts that generate and validate platform bindings, and the file-touch-discipline rule for committing generated mirrors alongside their source. Read this when you need the exact command to generate or validate binding artifacts, or when deciding which commit a regenerated mirror file belongs in.
- [Multi-Harness Binding: Related Documentation](./related.md) — Links to the platform-bindings catalog, the vendor-independence convention, and the periodic compatibility-audit workflow that complement this convention. Read this when you need the catalog, the vendor-neutral-prose companion rule, or the external-drift-detection workflow this convention cross-references.
