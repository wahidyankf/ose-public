# Multi-Harness Binding: Principles and Purpose

Why this convention exists and which principles it implements. Part of the
[Multi-Harness Binding Convention](../multi-harness-binding.md).

## Principles Implemented/Respected

- **[Simplicity Over Complexity](../../../principles/general/simplicity-over-complexity.md)**: One
  canonical instruction surface (`AGENTS.md`) rather than one maintained copy per harness. Thin
  binding tiers (native read or pointer) minimize the surface that must stay consistent.

- **[Explicit Over Implicit](../../../principles/software-engineering/explicit-over-implicit.md)**: The
  two-tier model, the no-shadowing rule, and the catalog requirement make every binding a deliberate,
  documented decision rather than an undiscovered hand-edited file.

- **[Automation Over Manual](../../../principles/software-engineering/automation-over-manual.md)**:
  Binding files that must exist are generated by the repo's CLI tooling from `AGENTS.md`, so they
  cannot drift. A deterministic parity guard, the `harness-adapters` gate, runs on the pre-commit and pull-request
  surfaces to enforce byte-equality.

- **[Documentation First](../../../principles/content/documentation-first.md)**: Every committed
  binding directory must have a catalog entry in `docs/reference/platform-bindings.md` before (or at
  the same time as) the files reach the main branch.

## Purpose

AI coding-agent harnesses differ in which files they read for project instructions. Some read
`AGENTS.md` natively; others require a harness-specific file. Without a governing convention, each
integration attempt risks:

- **Instruction duplication** — the same content maintained in multiple files, drifting apart over
  time.
- **Silent shadowing** — a harness-specific file ranked above `AGENTS.md` whose content diverges,
  giving that tool different instructions than every other tool.
- **Unbounded proliferation** — harness-specific directories added ad-hoc with no catalog, no
  generator, and no parity check.

This convention prevents all three failure modes by establishing a two-tier model, a hard
no-shadowing rule, a mechanical-generation requirement, and a deterministic parity guard gated at pre-commit and pull request.
