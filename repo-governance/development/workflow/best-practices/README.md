# Best Practices for Workflow Development

- [Practice 1: Integrate Continuously via Short-Lived Branches](./practice-1-integrate-continuously-via-short-lived-branches.md) — Keep every branch short-lived and single-purpose; TBD forbids long-lived branches, not branches. Use when starting a plan branch, to confirm it will integrate within a day or two rather than living long-term.
- [Practice 2: Make Small, Frequent Commits](./practice-2-make-small-frequent-commits.md) — Compose the fewest build-valid, reviewable, revertible commits. Use after explicit authorization when choosing boundaries.
- [Practice 3: Use Conventional Commits](./practice-3-use-conventional-commits.md) — Follow conventional commit format for clear, parseable history. Use when writing a commit message and choosing its type/scope/subject format.
- [Practice 4: Use Feature Flags Instead of Long-Lived Branches](./practice-4-use-feature-flags-instead-of-long-lived-branches.md) — Integrate internally complete-and-inert behaviour behind a temporary production-disabled flag, with both paths tested and rollout, rollback, and removal recorded. Use when incomplete behaviour must merge without production exposure.
- [Practice 5: Implement in Three Stages](./practice-5-implement-in-three-stages.md) — Make it work, then make it right, then make it fast. Use when planning implementation order for a new feature, to sequence correctness before optimization.
- [Practice 6: Pin Dependencies for Reproducibility](./practice-6-pin-dependencies-for-reproducibility.md) — Lock versions using package-lock.json and Volta. Use when adding a dependency or configuring runtime/tool version pinning.
- [Practice 7: Keep CI Green at All Times](./practice-7-keep-ci-green-at-all-times.md) — Never commit code that breaks CI, fix immediately if broken. Use when CI fails after a push, to confirm the correct response is an immediate fix or revert.
- [Practice 8: Use Environment-Specific Configuration](./practice-8-use-environment-specific-configuration.md) — Different settings for development vs production, never hardcoded. Use when a value differs between local development and production and needs to be configured rather than hardcoded.
- [Practice 9: Split Independent Concerns](./practice-9-split-independent-purposes.md) — Split independent purposes while keeping required cross-domain completion artifacts together. Use when a change set contains multiple potential purposes.
- [Practice 10: Test Before Committing](./practice-10-test-before-committing.md) — Run tests locally before every commit rather than waiting for CI. Use immediately before committing, to confirm tests and lint were run locally first.
- [Practice 11: Pull with Rebase Before Pushing](./practice-11-pull-with-rebase-before-pushing.md) — Always pull latest changes from remote main before pushing, preferring rebase for clean linear history in Trunk Based Development. Use immediately before pushing to main, to pull the latest remote changes with rebase first.
- [When to Use Merge vs Rebase](./when-to-use-merge-vs-rebase.md) — Rebase is the default for daily TBD workflow; five conditions where merge is the safer choice instead. Use when deciding whether to pull with rebase or merge for a specific situation.
- [Git Configuration for Rebase](./git-configuration-for-rebase.md) — Three ways to configure git to pull with rebase by default — branch-specific, global, or explicit flag. Use when setting up a repository or global git config so pulls rebase by default instead of merging.
- [Conflict Resolution Workflows](./conflict-resolution-workflows.md) — How to resolve conflicts during a rebase versus during a merge, and the decision tree for choosing between them. Use when a pull produces conflicts, to work through resolving them under rebase or merge.
- [Safety Considerations](./safety-considerations.md) — Never rebase commits others have pulled; when unsure prefer merge; and how to abort a rebase or merge safely. Use before rebasing pushed commits, or when a rebase/merge needs to be safely aborted.
- [Best Practice in Daily Workflow](./best-practice-in-daily-workflow.md) — A worked start-of-day-to-push walkthrough using rebase, including what to do when a conflict appears. Use as a concrete daily-workflow template combining rebase config, pulling, committing, and pushing.
- [Practice 12: Default to worktree-to-pr; Never Assume a Direct-Push Mode](./practice-12-default-to-worktree-to-pr.md) — The repo-wide default delivery mode is worktree-to-pr; direct-push modes have no executable path in ose-public, so they are never the assumed path. Use when choosing a plan's delivery mode, to confirm worktree-to-pr is the default and the only available mode.
- [Summary and Principles/Conventions Implemented](./summary-and-principles-conventions-implemented.md) — Recap of all twelve best practices, plus the principles and conventions they implement. Use as a quick recap of all twelve practices, or when tracing them back to the principles and conventions they implement.
