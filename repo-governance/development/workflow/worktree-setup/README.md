# Worktree Toolchain Initialization

- [Principles and Conventions Implemented](./principles-and-conventions-implemented.md) — The principles the worktree toolchain initialization practice respects, and its lack of a direct Layer 2 convention. Use when tracing why the two-step worktree init exists back to the principles it respects.
- [The Rule](./the-rule.md) — The mandatory guarded-install and read-only Doctor sequence, run order, and the drift-only transactional provisioning branch. Use as the exact commands to run, in order, right after creating a worktree.
- [Independent Drift Layers and the `postinstall` Hook](./independent-drift-layers-and-the-postinstall-hook.md) — The two independent kinds of toolchain drift a worktree session can hit, and why the postinstall hook's error-swallowing means only the explicit Doctor validation surfaces drift. Use when explaining why the guarded install and the explicit Doctor validation are independently required, not either alone.
- [Dependency Isolation, Language Breadth, and Idempotency](./dependency-isolation-language-breadth-and-idempotency.md) — Why node_modules is not shared across worktrees, why worktrees routinely need many language toolchains, and why read-only Doctor validation is cheap to run on creation regardless of stated task scope.
- [What Goes Wrong Without Both Steps, and Nx's `node_modules` Dependency](./what-goes-wrong-and-nx-node-modules-dependency.md) — The concrete failure modes (build, test, lint, cache, cryptic errors) from skipping the two-step init, and why Nx's caching depends on consistent node_modules state. Use when diagnosing a build, test, lint, or Nx-cache failure that may trace back to a skipped worktree init step.
- [Per-Project Dependency Restoration for Some Language Ecosystems](./per-project-dependency-restoration.md) — The per-project restore gap for F#/.NET projects, which need an explicit dotnet restore step that toolchain validation and provisioning do not cover. Use when `nx affected -t test:quick` fails on an F# project with a missing-dependency error right after provisioning a worktree.
- [Per-Project Generated Sources](./per-project-generated-sources.md) — The init gap for projects whose generated sources are gitignored, which need their own codegen target run once before a language server or build can resolve them. Use when an editor or build reports an unresolved import naming a generated package right after provisioning a worktree.
- [Sibling-Repo Relative Paths From Inside a Worktree (Multi-Repo Plans)](./sibling-repo-relative-paths.md) — Why a naive ../sibling-repo path breaks from inside a worktree, and the correct nesting-adjusted relative path for a multi-repo worktree-to-pr plan. Use when authoring or reviewing a multi-repo delivery-checklist command that references a sibling repo with a relative path.
- [Absolute Source Paths in Delivery-Checklist Commands (Same-Repo Worktree vs. Primary Checkout)](./absolute-source-paths-in-delivery-checklist-commands.md) — Why a hardcoded absolute path to a repo's primary checkout silently resolves to stale content instead of the worktree's in-progress copy, and how to verify it before running. Use before running any delivery-checklist command that reads from an absolute path into a repo the same plan is also modifying.
- [When This Applies](./when-this-applies.md) — The creation triggers for the two-step worktree init, and that it applies regardless of stated task scope.
- [Step-by-Step Procedure](./step-by-step-procedure.md) — The five numbered steps from creating a worktree through confirming both init commands completed. Use as a walkthrough when creating a worktree and running its toolchain init for the first time.
- [Notes for AI Agents](./notes-for-ai-agents.md) — The MUST-run-both-steps rule for agents, and why re-running the init (not re-provisioning) is the correct response to missing worktree dependencies mid-session. Use when an agent creates a worktree or discovers missing dependencies/build output mid-session.
